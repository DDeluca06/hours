# Findings — 2026-08-18

Investigation into two symptoms observed while compiling a day's hours:

1. `reconstruct_day` reporting `wakapi network error: fetch failed`.
2. Inferred blocks arriving as long multi-hour stretches rather than distinguishable
   pieces of work.

Everything below was measured on this machine on 2026-08-18, against 59 real signals.
Line references are to the tree as it stood at `7fcbd18`.

---

## 1. The wakapi outage was a stop, not a crash

The container exited **code 2 at 13:23:05Z (09:23 local)** — the start of the workday —
and stayed down for six hours.

Evidence that it was stopped deliberately rather than failing:

- `restart: unless-stopped` did **not** restart it. Docker only skips the restart when a
  container was explicitly stopped.
- No error line in the logs. The last entry is a routine leaderboard job at 13:09Z.
- SQLite shut down cleanly — no `-wal` / `-shm` file beside `data/wakapi.db`.
- `OOMKilled=false`; 311G free on `/home`.

`docker compose up -d` in `~/wakapi` brought it back with no data loss; the compat
endpoint serves 2026-08-17 again (80 heartbeats, 40 `is_write`).

**Cause not established.** The stop coincides with unrelated homelab SSH / deploy /
"autoheal" work that shows up in the same morning's unattributed signal stream
(09:38–10:43). Plausible, not proven.

### The outage cost nothing that day, and that is the real problem

Even with the server up, heartbeat coverage for 2026-08-18 would have been **zero**:

- `~/.wakatime/offline_heartbeats.bdb` and `wakatime-internal.cfg` were last written
  **2026-08-17 15:04**. wakatime-cli had not run at all that day, so there was nothing
  buffered to flush.
- VSCodium *was* running, but `~/.config/VSCodium/User/History` had **0** files touched
  that day.

Every edit came from an agent harness writing files directly, which produces neither a
wakatime heartbeat nor an editor-history entry. **Heartbeat and editor-save coverage is
structurally near-zero on agent-driven days.** Both sources only see work you type
yourself. On such days the day rests entirely on git commits and harness turns.

Worth stating in `docs/harnesses.md` as a coverage limit rather than leaving it to be
rediscovered: a green sweep with `wakapi=0` is indistinguishable from a quiet afternoon,
which is the exact failure `heartbeatShapeWarning` was written to catch one layer down.

## 2. `reconstruct_day --dryRun` discards its own output

A dry run reports **nothing at all**, however much it inferred:

```
2026-08-18 — read 59 signal(s)
(dry run — nothing written)
```

Two lines conspire:

- `apps/collector/src/reconstruct.ts:90-92` returns `created: []` on every dry run,
  keeping only `unattributed`. The attributed blocks are computed *and* task-attributed
  (the comment at `:60` says reporting them "is the point of the dry run") and then
  dropped on the floor.
- `apps/mcp-server/src/index.ts:672-679` prints `(dry run — nothing written)` and gates
  the whole `reasoning:` section on `out.created.length`, so an empty `created` prints
  no blocks and no provenance.

When the unattributed blocks are also empty — normal, since `clipAgainst` removes any
that overlap attributed time — the output is two lines that look like an inference
failure.

Running `inferBlocks` directly over the same 59 signals produced **7 blocks / 285m**:

| Window | Min | Project | Activity | Signals | Confidence |
|---|---|---|---|---|---|
| 09:30–10:45 | 75 | lp | Development | 8 | 0.75 |
| 10:45–11:30 | 45 | north10 | Misc | 4 | 0.75 |
| 12:00–12:15 | 15 | lp | Misc | 3 | 0.75 |
| 12:15–12:30 | 15 | north10 | Scoping | 4 | 0.65 |
| **13:00–14:45** | **105** | north10 | Development | **20** | 0.85 |
| 14:45–15:00 | 15 | lp | Development | 4 | 0.30 |
| 15:00–15:15 | 15 | lp | Development | 6 | 0.85 |

**Fix shape:** have `reconstruct` return the inferred blocks in dry-run mode (a separate
`would_create` field, or `created` typed as block-or-entry) and have the MCP handler
render them. A dry run that cannot show what it would write has no reason to exist.

## 3. Long stretches are `gapMin` measured against the wrong signal density

`policy.gapMin = 25` splits a run only when an idle gap exceeds 25 minutes. Actual gaps
between consecutive signals within a project stream, 2026-08-18:

| Stream | Signals | Gaps > 25m | Gaps ≤ 25m | Median gap |
|---|---|---|---|---|
| lp | 21 | 3 | 17 | **4.6m** |
| north10 | 28 | 2 | 25 | **1.3m** |
| unattributed | 10 | 0 | 9 | 0.7m |

Agent turns fire every one to five minutes. A 25-minute bridge is therefore enormous
relative to signal density, and it welds an entire afternoon into a single run: the 105m
`north10` block above is a chain of **20 signals from 12:53 to 15:08 in which no single
gap exceeds 25 minutes**. 2026-08-14 has the same shape — 50 `north10` signals, only 2
gaps over 25.

`gapMin` was calibrated for commits, which are sparse. It was never re-examined against
harness turns, which are dense.

### Sensitivity, everything else held fixed

| gapMin | Blocks | Total | Longest block |
|---|---|---|---|
| 25 | 7 | 285m | 105m |
| 15 | 11 | 300m | 105m |
| 10 | 12–13 | 300–315m | **60m** |

Two results worth keeping:

- **`leadInMin` is irrelevant here.** Total is **285m at leadIn 20, 10, and 0** —
  identical. Runs mostly open on a measured span, which skips the lead-in by design, and
  rounding absorbs the remainder. Tuning it would change nothing.
- **Long stretches under-report; they do not over-bill.** Tightening `gapMin` 25→10
  *raises* the day's total from 285m to 315m. Longer blocks from two interleaved projects
  overlap more, and `resolveOverlaps` discards the loser's minutes. The bridge is costing
  billable time, not inventing it.

Changing `gapMin` is a policy decision, not a bug fix, and it will shift comparisons
against days already pushed. Recorded here rather than acted on.

## 4. Two smaller defects found on the way

**The workday clamp is silently truncating the end of the day.** `endMin: 900` (15:00)
with `allowOutsideWorkday = false`. `.env` contains `HOURS_ALLOW_OUTSIDE=` — *present but
empty*, which `loadConfig` reads as false via `=== '1'`. Work after 15:00 is discarded:
on 2026-08-18 that clipped `north10` activity running to 15:08 and `lp` to 15:16. It also
means the 7:35 PM and 9:09 PM entries on 2026-08-14 cannot have come from reconstruction —
they were logged by hand.

An empty-string env var reading as a hard `false` is worth a second look; elsewhere in the
loader (`DATABASE_URL`, the OpenProject and wakapi credentials) empty is explicitly
treated as *unset* so a copied `.env.example` behaves like an absent one. `allowOutside`
does not follow that convention.

**A block can escape the workday window after being clamped.** In
`packages/core/src/blocks.ts`, a run whose clamped range rounds into a single slot is
given one granule:

```ts
if (endMin <= startMin) endMin = startMin + policy.roundToMin;
```

Applied *after* `clampToWorkday`, so it can push `endMin` past `policy.endMin`. This is
what emitted the **15:00–15:15** `lp` block above — outside the 9–15 window despite
`allowOutside = false`. Harmless in size, but it defeats the clamp after the fact.
